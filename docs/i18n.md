# Internationalization and Localization

The application must be usable in both German and English. German is expected
to be the primary operational language for many users, while English must also
be fully supported for administrators, mixed teams, and future maintainability.

## Supported languages

MVP languages:

- German: `de`
- English: `en`

Recommended default:

- Use German as the default production UI language if the deployment is for a
  German-speaking operations team.
- Keep English available through a language selector.

## Scope

Translate all user-facing text:

- Navigation labels.
- Page titles.
- Form labels.
- Field help text.
- Validation messages.
- Error messages.
- Empty states.
- Status labels.
- Workflow step names.
- Buttons and action labels.
- Dashboard cards.
- Table column headers.
- PDF protocol labels.
- Excel import result messages.
- Authentication screens.
- Admin-facing frontend screens.

Backend API field names should remain stable and language-neutral in English
for developer ergonomics. User-facing labels returned by the API may be
localized where needed.

## Frontend implementation requirements

- Use an i18n library such as `react-i18next`, `i18next`, or an equivalent
  established solution.
- Keep translations in structured resource files, for example:

```text
frontend/src/i18n/
├── index.ts
├── locales/
│   ├── de/common.json
│   ├── de/vehicles.json
│   ├── de/workflows.json
│   ├── en/common.json
│   ├── en/vehicles.json
│   └── en/workflows.json
```

- Do not hard-code user-facing text directly in components.
- Add a language selector in the authenticated layout.
- Persist the selected language in local storage or user profile settings.
- Detect browser language on first visit, then allow manual override.
- Use locale-aware date, time, and number formatting.
- Keep validation messages translatable.
- Add tests or lint rules that catch common missing translation keys.

## Backend implementation requirements

- Keep API codes, enum values, and database values stable and language-neutral.
- Localize backend-generated validation messages where they are shown directly
  to users.
- PDF generation must support German and English labels.
- Store the language used for each generated PDF protocol so the document can
  be reproduced or audited.
- Excel import errors should be returned in the active user language where
  practical.
- Consider Django's built-in translation framework for backend messages:
  `gettext_lazy`, locale middleware, and translation catalogs.

## PDF protocol requirements

PDF protocols must be generated in the selected language.

Each PDF should include:

- Localized document title.
- Localized field labels.
- Localized status labels.
- Localized date/time formatting.
- A stored language code, for example `de` or `en`.

Recommended German PDF titles:

- `Fahrzeug-Übernahmeprotokoll`
- `Fahrzeug-Ausleihprotokoll`
- `Fahrzeug-Rückgabeprotokoll`
- `Hersteller-Rückgabeprotokoll`

Recommended English PDF titles:

- `Vehicle Check-In Protocol`
- `Vehicle Loan Protocol`
- `Vehicle Return Protocol`
- `Manufacturer Check-Out Protocol`

## Acceptance criteria

- A user can switch between German and English.
- The selected language persists across page reloads.
- Main workflows are fully translated in both languages.
- Dashboard, vehicle pool, vehicle detail, workflow wizards, and admin import
  screens are translated.
- Validation and error messages are available in both languages.
- PDF protocols can be generated in German and English.
- Status values are stored as stable codes and displayed as translated labels.
- Automated checks cover at least the presence of required translation keys for
  both languages.

## Agent guidance

Every implementation agent must treat user-facing text as translatable from the
beginning. If an agent adds a UI screen, PDF label, validation message, or
workflow status display, it must add or update both German and English
translations in the same change.
